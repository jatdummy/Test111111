# Claude Code 행동 규칙

> Claude Code가 이 프로젝트에서 반드시 따라야 하는 행동 규칙

---

## 행동 원칙

### 1. 사고 우선 (Think Before Coding)

> 가정을 숨기지 말고, 모호하면 멈춘다.

- 가정을 명시적으로 말한다. 불확실하면 질문한다.
- 해석이 여러 갈래라면, 모두 제시하고 임의로 고르지 않는다.
- 더 단순한 방법이 보이면 사용자에게 알린다.
- 확인 결과는 아래 검증 등급으로 표기한다. 이 프로젝트의 모든 문서와 에이전트는 이 정의를 따른다.

| 등급 | 기준 |
|---|---|
| 검증 | 도구를 실행한 결과로 확인했다. (테스트 실행, 명령 출력, Unity MCP 조회 등) |
| 코드 확인 | 소스코드나 파일을 읽고 대조해서 확인했다. |
| 미검증 | 위 둘 다 아니다. (에디터 설정, 씬 / 프리팹 연결, 실행 중 동작 등. Unity MCP가 켬이면 `Unity MCP 사용 규칙`에 따라 `검증`이 될 수 있다) |

### 2. 단순함 우선 (Simplicity First)

> 문제를 푸는 최소한의 코드만 작성하라.

- 요청 범위 밖의 기능을 추가하지 않는다.
- 한 번만 쓰는 코드에 추상화를 도입하지 않는다.
- 요청하지 않은 "확장성"이나 "가능성"을 미리 만들지 않는다.
  - 연결 Issue의 `목표 (To-be)`나 승인된 브리핑에 명시된 구조는 요청된 것으로 본다.
- 일어날 수 없는 상황을 위한 예외처리를 작성하지 않는다.

### 3. 외과적 변경 (Surgical Changes)

> 필요한 곳만 건드려라.

- 인접 코드, 주석, 포맷팅을 임의로 "개선" 하지 않는다.
- 구동에 문제가 없는 코드를 리팩토링 하지 않는다.
- 본인 변경 때문에 쓰이지 않게 된 변수, 함수는 정리한다. 원래 있던 죽은 코드는 보고만 한다.

**판단 기준** : 변경을 가하는 모든 행위는 사용자의 결정에서 직접 나와야 한다.

### 4. 검증 가능한 목표 (Goal-Driven Execution)

> 성공 기준을 먼저 정하고, 확인될 때까지 진행한다.

- 작업 계획은 `WorkflowRules.md` `4. 브리핑` 양식의 `작업 순서` 형식(`단계 -> 확인 : 항목`)으로 세운다. (브리핑 생략 예외는 `WorkflowRules.md` `1. 업무 유형`)

## 작업 범위 규칙

- 요청(승인)받은 파일과 기능 외의 코드는 수정하지 않는다.
- 범위 밖 문제를 발견했을 때의 처리는 `WorkflowRules.md` `5. 업무 수행 (업무 착수)`의 `중단 조건`을 따른다.

## Unity MCP 사용 규칙

> Unity MCP에 관한 규칙의 단일 출처다. `Docs/TechSpec.md` `5. 도구 연결`의 `Unity MCP 사용`이 `켬`일 때만 적용한다. `끔`이면 Unity MCP를 사용하지 않는다.

### 조회

- 조회는 Unity의 상태를 바꾸지 않는 호출이다. 사용할 조회 도구와 허용 action은 `Docs/TechSpec.md` `5. 도구 연결`의 `조회 도구`에 적힌 것만 쓴다.
- 한 도구 안에 조회 action과 변경 action이 섞여 있으면 조회 action만 호출한다. 권한 설정은 도구 이름 단위라서 action을 막지 못하므로 이 규칙으로 지킨다.
- 메인과 서브에이전트 모두 조회를 사용할 수 있다. 서브에이전트는 자기 `tools`에 들어 있는 조회 도구만 사용한다.
- 조회로 대신 확인할 수 있는 항목 : Unity 콘솔의 Error / Warning 로그, 씬 / 프리팹의 컴포넌트와 참조 연결 상태.

### 검증 등급

- 조회 결과는 아래를 모두 확인했을 때만 `검증` 등급이다.
  1. 마지막 스크립트 변경 뒤 Unity가 다시 컴파일했다. (새로고침이 필요하면 `Docs/TechSpec.md` `5. 도구 연결`의 `새로고침 도구`를 메인이 실행하거나, 사용자에게 Unity 에디터를 한 번 선택해 달라고 요청한다)
  2. 에디터가 컴파일 중이 아니다. (에디터 상태를 조회하는 도구로 확인한다)
  3. 그 시점 이후의 콘솔 로그나 상태를 조회했다.
- 위 확인이 하나라도 안 되거나, 조회 도구를 쓸 수 없으면(도구 없음, 서버 미연결, 권한 거부, 에디터 미실행) `미검증`이다.
- PR 체크와 DoD 판정에 쓰는 콘솔 결과는 PR 생성 직전에 메인이 이 절차로 다시 조회한 결과만 쓴다. (`Docs/Documentation/GithubPRRule.md` `2. 연결 Issue`)

### 변경

- 씬, 프리팹, 에셋, 에디터 설정을 바꾸는 MCP 호출은 아래 조건을 모두 만족할 때만 메인이 한다. 서브에이전트는 변경 호출을 하지 않는다.
  1. 승인된 브리핑의 `생성/수정/삭제 파일`에 바꿀 대상의 경로가 적혀 있다. (에디터 설정이면 해당 `ProjectSettings/*.asset` 경로)
  2. 실행 직전에 바꿀 대상과 내용을 사용자에게 보여 주고 확인받았다.
- 브리핑의 작업 순서에서 MCP 변경 단계는 `(메인, MCP 변경)`으로 표시한다. 작성자와 검수자는 이 단계를 미이행이나 범위 위반으로 보지 않는다.
- 시점은 `WorkflowRules.md` `5. 업무 수행 (업무 착수) > 검수 반복`이 `통과`하고, 위 `검증 등급`의 1~2번을 확인한 뒤다. 바꾼 직후 메인이 조회 도구로 대상 상태를 다시 조회하고, 바꾼 대상과 내용, 조회 결과와 등급을 검수 요청에 포함한다.
- 아래는 MCP로 하지 않는다.
  - C# 파일의 생성, 수정, 삭제. (소스코드는 `WorkflowRules.md` `5. 업무 수행 (업무 착수)` 절차로만 작성한다)
  - 임의 코드 실행, 메뉴 실행, 여러 호출을 묶어 실행하는 도구.
- Play 모드 진입과 테스트 실행은 변경으로 보고, 사용자에게 확인받은 뒤 메인만 한다.
